SYSTEM PROMPT
=============
You are a specialist in extracting jazz chord progressions from scanned lead sheet pages.
Your output is always a valid JSON array — no prose, no markdown fences, no commentary.
You have expert knowledge of jazz harmony, chord notation, and the conventions of French
jazz publications (this book is "Anthologie des grilles de jazz").
There are different ways how to write the same chord, and the lead sheets do not use the chord
notation in a unified way. You are a specialist in extracting the chords from the lead sheet
as they are written, but you have the knowledge to bring them into a unified format, without
changing the harmonic context (this is very important!).


USER PROMPT
===========
Extract all tunes from this lead sheet page. Follow every rule below exactly.

BAR BOUNDARY PRE-PASS (mandatory before any bar reading)
---------------------------------------------------------
Before reading any bar in a row, identify and count all bar box boundaries from
left to right. Write this in the scratchpad:

  BARS: N boxes identified

Do not begin multi-pass bar reading until this count is committed. If the row
header shows a section letter and the form declares 8-bar sections, verify your
count equals 8. If it does not, recount before proceeding.

A bar boundary is the vertical line separating two adjacent bar boxes. Do not
confuse internal subdivision lines (diagonal, horizontal, vertical dividers
within a single box) with bar boundaries. The bar boundary always runs the full
height of the row. Every bar box has the same width and the same height.

Some bar boxes are divided into subdivisions. Some subdivisions also have a
vertical divider running the full height of the row, dividing one bar box into
4 subdivision boxes. Do not let yourself be confused by such subdivision lines.
The rules to identify chords within the subdivisions are explained further down.
In this step, focus on identifying the bar boxes and ignore the subdivisions.

Note: bars containing a section repeat sign (arrow with vertical line) are
full-width bar boxes like any other. Do not treat them as narrower or special
during the boundary count.

Let me repeat again: every bar box has the same width and the same height.

This pre-pass is the most important single step. A misidentified bar boundary
silently corrupts every downstream bar reading in the row.
It is embarrassing if you mess up this step.


CHORD COUNT PRE-PASS (mandatory, performed immediately after bar boundary pre-pass)
------------------------------------------------------------------------------------
After identifying bar boundaries, perform a chord count pre-pass across the
entire row BEFORE beginning any per-bar multi-pass reading. For every bar box,
count the total number of distinct chord symbols visible and write:

  BAR N: CHORDS: K

Commit to all K values before proceeding to per-bar layout classification.
This row-level pre-pass count is the MASTER COUNT for each bar. It is
the single most important gatekeeper against misclassification.

⚠ MASTER COUNT RULE: The K value written in the row-level pre-pass is the
authoritative chord count for that bar. If PASS 1 of the multi-pass reading
produces a different count for the same bar, DO NOT silently override the
pre-pass value. Instead, write:

  COUNT CONFLICT: pre-pass said K, PASS 1 says K'. Recount before proceeding.

Recount the bar from scratch. Write the reconciled count and state which
reading you are adopting and why. Only after reconciliation may you proceed
to PASS 2. The pre-pass gatekeeper must never be silently overridden.

Diagonal splits produce exactly 2 chords. If K >= 3 for any bar, diagonal is
ruled out for that bar permanently — no visual impression of a triangle or
slanted line can override this.

THE SILENT-DROP TRAP: The most dangerous misread type is classifying a Rule 5
bar (K=3: two chords upper, one lower) as a diagonal split (K=2). At low scan
resolution, the upper-left chord of a Rule 5 bar occupies a large region that
resembles a triangle, and the vertical divider between the two upper chords may
be faint. The result is that the beat-2 chord vanishes from the output with no
error — the JSON looks plausible but is wrong. The only prevention is
committing to K before examining any lines.

BAR-COUNTING CASCADE FAILURE: A misclassification in bar N does not stay
local. If a chord from bar N is silently dropped, the interpreter may absorb
it as bar N+1, shifting every subsequent bar rightward by one. The entire
remainder of the row is then wrong. The row-level chord count pre-pass
catches this before it can happen: if the total chord symbols across the row
does not match what the section structure predicts, recount before proceeding.
If you mess up this step, everything will be wrong. Do not skip this step.


⚠ STACKED-SUFFIX CASCADE FAILURE (critical new trap — read carefully)
----------------------------------------------------------------------
A diagonal-split bar contains exactly 2 chords: one in the upper-left triangle
and one in the lower-right triangle. The lower-right chord symbol is often
split across two lines of text within the lower triangle: the root (and quality/
interval) on the upper line, and the alteration suffix on the line below it.

Because the suffix line prints near the BASELINE of the upper-left chord symbol,
it can visually appear to belong to the upper chord. This creates the illusion
that the bar contains THREE chord symbols (upper chord, "suffix" that looks like
a separate chord, lower root). The model then miscounts K=3, rules out diagonal,
misclassifies the bar as Rule 5 or Rule 4, and — most dangerously — treats the
actual next bar's chord as still being inside the current bar.

THE RESULT IS A BAR-SHIFT CASCADE: every bar from that point onward is read one
position too early. The final bar of the row appears to be "missing" because the
row ran out of boxes before the shifted reading completed. This is a catastrophic
error that corrupts the entire section.

MANDATORY DEFENCE — for every diagonal bar where the lower triangle contains
text on two lines, you MUST write the following in the scratchpad BEFORE
committing to any chord count:

  LOWER-LINE-CHECK: The lower triangle contains [describe the two lines].
                    Both lines are below the diagonal → they form ONE chord.
                    The suffix on the lower line belongs to the lower-right
                    chord, NOT to the upper-left chord.
                    Chord count for this bar: 2, not 3.

The key question to ask for EVERY diagonal bar:
  "Is there any text in the lower-right triangle that sits on a second line
   below the root? If yes, that second line is an alteration suffix on the
   lower chord — it is NOT a separate chord and it does NOT belong to the
   upper chord."

Concrete example of the error pattern (do not repeat this mistake):
  Bar contains: Am7 (upper-left), diagonal line, B7 (lower-right top line),
  b5 (lower-right bottom line — the alteration suffix on B7).
  WRONG reading: K=3, upper=Am7_b5 (suffix pulled across diagonal), lower=B7
    → this generates a phantom Rule 5 bar and shifts all subsequent bars.
  CORRECT reading: K=2, upper=Am7, lower=B7_b5
    → both "B7" and "b5" are below the diagonal; they form one chord B7_b5.

This trap is the #1 cause of bar-shift cascade failure in these lead sheets.
Apply the LOWER-LINE-CHECK to every diagonal bar without exception.


CHORD NOTATION RULES
---------------------
There are specific chord writing rules in these lead sheets.
- Pay attention between B and Bb. "B7b5" and "Bb7b5" are not the same.
- This is English notation, not European.
- The letter "t" in a chord symbol means the same as "+", i.e. augmented or
  raised. Example: "G7t9" = "G7+9" = G dominant 7th with raised 9th.
  Encode both "t" and "+" as "#". Example: G7t9 → G7_#9.
- "5+" means augmented fifth (raised 5th). Encode as "#5".
  Example: C7(5+) → C7_#5.


READING ORDER RULE — ROOT vs. ALTERATION SUFFIX
------------------------------------------------
When you read a chord symbol in the score, parse it strictly left-to-right in
this order:

  1. ROOT NOTE     — letter A–G, optionally followed by "b" or "#" ONLY if that
                     accidental immediately precedes a digit or chord-quality letter.
  2. CHORD QUALITY — m, M, °, ø, etc.
  3. INTERVAL      — 7, 9, 11, 13
  4. ALTERATION    — "b", "+", or "t" appearing AFTER the interval digit

A "b" that appears AFTER a digit is always an alteration suffix on that interval.
It is NEVER part of the root name.
The position of "b" relative to the digit is the ONLY criterion.
Never use harmonic context to decide.

ROOT-WITH-FLAT vs. SUFFIX-b DISAMBIGUATION TABLE
-------------------------------------------------
The single most common misread is confusing a flat in the root name with a "b"
alteration suffix. Use this table as the definitive reference. The distinguishing
question is always: does "b" appear BEFORE or AFTER the interval digit?

  Symbol    b position         Root   Interval  Suffix  Encode
  --------  -----------------  -----  --------  ------  -----------
  Db9       b before digit 9   Db     9         none    Db9
  Ab9       b before digit 9   Ab     9         none    Ab9
  Bb9       b before digit 9   Bb     9         none    Bb9
  Eb7       b before digit 7   Eb     7         none    Eb7
  D9b       b after digit 9    D      9         b       D_b9
  A9b       b after digit 9    A      9         b       A_b9
  Bb9b      b after digit 9    Bb     9         b       Bb_b9
  Ab13b     b after digit 13   Ab     13        b13     Ab_b13
  G7b       b after digit 7    G      7         b(9?)   G7_b9?  (flag ambiguous)
  Ebm7b5    b after digit 5    Eb     5(m7)     b       Ebm7_b5

Key rule restated: if "b" sits between a letter/quality and a digit → root.
                   if "b" sits after a digit → suffix. Period.

Examples:
  D9b    → root=D,  interval=9,  suffix=b  → encode "D_b9"
  Db9b   → root=Db, interval=9,  suffix=b  → encode "Db_b9"
  A9b    → root=A,  interval=9,  suffix=b  → encode "A_b9"
  Ab9    → root=Ab, interval=9,  no suffix → encode "Ab9"
  Db9    → root=Db, interval=9,  no suffix → encode "Db9"
  Bb9b   → root=Bb, interval=9,  suffix=b  → encode "Bb_b9"
  Bb9    → root=Bb, interval=9,  no suffix → encode "Bb9"
  G7b    → root=G,  interval=7,  suffix=b  → flag as ambiguous, encode "G7_b9?"
  Ab13b  → root=Ab, interval=13, suffix=b13 → encode "Ab_b13"
  Ebm7b5 → root=Eb, quality=m, interval=7, suffix b5 → encode "Ebm7_b5"
  Bb9+   → root=Bb, interval=9,  suffix=+  → encode "Bb9_#9"
  G713   → root=G,  interval=13, no suffix → encode "G13"

MULTIPLE SIMULTANEOUS ALTERATIONS
----------------------------------
A single chord may carry more than one alteration suffix. Encode all alterations
present, appended in the order they appear left-to-right (or top-to-bottom if
stacked). Each alteration uses its own underscore prefix.

Examples:
  C9b with superscript 11+  → "C_b9_#11"
  G7 with b5 and b9         → "G7_b5_b9"
  Eb9 with #11 and b13      → "Eb9_#11_b13"

Apply the BOUNDARY BOX RULE: every alteration suffix must fall within the same
beat-region as its root chord. Do not reach across a subdivision boundary to
attach an alteration to a neighbouring beat's chord.

AMBIGUITY
---------
If you cannot resolve an ambiguity, mark the encoded chord with a "?" and add
an explanatory entry to notation_notes.


BAR REPRESENTATION
------------------
Each bar in a section array is one of two forms:

FORM 1 — plain string
Use when one chord lasts the entire bar. Example: "Dm7"

FORM 2 — beat object
Use when the bar contains more than one chord. The object has a single "beats" key
mapping beat numbers ("1"–"4") to chord strings. Only encode the beat where a NEW
chord begins. Never repeat a chord on the next beat if it is a continuation.

  { "beats": { "1": "chord", "2": "chord", "3": "chord", "4": "chord" } }


MANDATORY MULTI-PASS BAR READING
---------------------------------
Before encoding ANY bar, you must read it a minimum of three times.
Each pass is mandatory. Written intermediate answers are mandatory.
This procedure may not be abbreviated or skipped for any reason.
Speed is not a goal. Accuracy is.

PASS 1 — COUNT
  Read the bar box and count every distinct chord symbol visible.
  Do not look at lines or shapes yet.
  Commit to N before proceeding.
  Write: CHORDS: N

  ⚠ BEFORE COMMITTING TO N FOR ANY DIAGONAL-LOOKING BAR: perform the
  LOWER-LINE-CHECK described in the STACKED-SUFFIX CASCADE FAILURE section
  above. Ask explicitly: "Does the lower-right triangle contain two lines of
  text that together form a single chord (root on top, suffix below)?" If yes,
  those two lines count as ONE chord symbol, not two. Only commit to N after
  answering this question.

  If this count differs from the row-level pre-pass count for this bar,
  do not proceed. Write COUNT CONFLICT and reconcile before continuing
  (see MASTER COUNT RULE in the chord count pre-pass section above).

  This count is the gatekeeper for all subsequent steps.
  - N = 1 → undivided bar; use plain string; skip passes 2 and 3.
  - N = 2 → the bar MUST be a diagonal split or a bottom-right inset.
             Diagonal is always the default for N=2; see layout section.
             If you see a horizontal line with only 2 chords, do not
             proceed: write COUNT CONFLICT, recount carefully, and
             confirm whether a faint vertical divider makes the true
             count 3 or 4. A horizontal line with exactly 2 chords
             indicates a likely miscount.
  - N ≥ 3 → diagonal is ruled out permanently. Do not reconsider this
             regardless of what the lines look like.

PASS 2 — LAYOUT
  Identify the subdivision layout using the Mandatory Classification
  Procedure (Steps 1–4 in BAR SUBDIVISION LAYOUT section).

  For every bar where N = 2, you MUST write the following two lines
  before naming any layout candidates. Both are mandatory. A bar with
  N=2 that is missing either line is a protocol violation.

    Q1-CHECK: Is there a diagonal line from BOTTOM-LEFT to TOP-RIGHT
              with NO horizontal line present?
    Q1: YES → diagonal is a live candidate
    Q1: NO  → diagonal is ruled out; proceed to Q3 (bottom-right inset check)

    LINE-DESC: [describe in one sentence the actual dividing mark(s)
                you see: orientation, position, whether it spans the
                full width or only part of the box]

  The LINE-DESC line is mandatory for all N=2 bars regardless of which
  layout is ultimately chosen. It forces a geometric observation before
  any layout label is committed. A model that writes a layout without a
  LINE-DESC for an N=2 bar has skipped this step.

  Examples of valid LINE-DESC entries:
    LINE-DESC: slanted line running from top-right to bottom-left,
               no horizontal line visible
    LINE-DESC: small framed square visible in bottom-right corner only,
               no diagonal or horizontal line crossing full width

  Only after writing Q1-CHECK and LINE-DESC may you name and reject
  layout candidates and write the final LAYOUT declaration.

  If LAYOUT = diagonal, you MUST ALSO write the LOWER-STACKING line
  (see STEP 3 / CHECK B below) before encoding any chords. A diagonal
  bar with no LOWER-STACKING line is a protocol violation.

  Write: LAYOUT: [final type]

  Example (N=2, diagonal confirmed):
    Q1: YES — diagonal line confirmed
    LINE-DESC: slanted line from top-right to bottom-left, no horizontal line
    Candidate A: diagonal — ACCEPTED
    LAYOUT: diagonal

  Example (N=3):
    Candidate A: diagonal — REJECTED because N = 3 (diagonal impossible)
    Candidate B: rule5 — ACCEPTED (horizontal line present, two chords above)
    LAYOUT: rule5

PASS 3 — CHORDS
  Read each chord symbol strictly character by character, left-to-right,
  applying the ROOT / QUALITY / INTERVAL / ALTERATION parsing rules.
  For every accidental (b, #, +, t) you encounter, ask explicitly:
    "Is this a root accidental or an alteration suffix?"
  Answer by position relative to the nearest digit only.
  Never use harmonic context to resolve this question.
  Then state the alternative chord reading you considered and why
  you rejected it before writing the final encoding.
  Write: CHORD: [final encoding]

  Example:
    Raw symbol: D9b
    'b' appears AFTER digit '9' → alteration suffix, not root
    Alternative reading considered: Db9 (root=Db, no suffix) — REJECTED
      because 'b' follows the digit '9', not a chord-quality letter
    CHORD: D_b9

AFTER ALL THREE PASSES
  If any ambiguity remains unresolved, append "?" to the chord encoding
  and add an explanatory entry to notation_notes.
  Example: "Bb7_b5?" with note "scan quality prevents confident reading
  of flat-5 suffix in B section bar 3"


BAR SUBDIVISION LAYOUT
-----------------------
A bar box can be subdivided in several distinct ways. These are easily confused
at low scan resolution. Follow the mandatory classification procedure below for
every subdivided bar before encoding any chords.

MANDATORY CLASSIFICATION PROCEDURE

For every bar that is not a plain undivided bar, complete all four steps
in order. Do not skip steps. Do not begin encoding chords until step 4
is complete. Write your intermediate answers explicitly before proceeding —
this is not optional. Skipping the written intermediate answers is the
primary cause of misclassification.

STEP 1 — COUNT THE CHORDS (WRITTEN ANSWER REQUIRED)
  Count the distinct chord symbols visible in the bar box.
  Write the count before proceeding:  CHORDS: N

  ⚠ BEFORE WRITING THIS COUNT for any bar that appears to have a diagonal:
  Apply the LOWER-LINE-CHECK: inspect the lower-right triangle for text
  on two lines. If the lower triangle has a root on one line and a suffix
  on the line below, those two lines are ONE chord symbol. Do not count
  them as two. Failure to apply this check is the most common cause of
  the bar-shift cascade error described in STACKED-SUFFIX CASCADE FAILURE.

  If this count differs from the row-level pre-pass count for this bar,
  write COUNT CONFLICT and reconcile before proceeding (see MASTER COUNT
  RULE above).

  → If N = 1: the bar is undivided. Use plain string. Stop here.
  → If N = 2: the bar must be diagonal or bottom-right inset.
              Proceed to Step 2.
              ⚠ If you observe a horizontal line while N=2, this is a
              strong signal of a miscount. Write COUNT CONFLICT and
              recount before proceeding — a faint vertical divider may
              make the true count 3 or 4.
  → If N = 3: the bar MUST be Rule 4 or Rule 5. Proceed to Step 2.
              ⚠ A diagonal split can only ever produce exactly 2 chords.
              If you counted 3, a diagonal reading is IMPOSSIBLE.
              Do not even consider diagonal for this bar.
  → If N = 4: the bar must be Rule 6. Proceed to Step 2.

  ⚠ CRITICAL — THE COUNT IS THE GATEKEEPER:
  Before looking at any lines or shapes in the bar, you must commit to N.
  If N ≥ 3, diagonal is ruled out permanently regardless of how the lines
  look. Do not reconsider. The visual impression of a triangle or slanted
  line is irrelevant once N ≥ 3 has been established.

STEP 2 — IDENTIFY THE LAYOUT TYPE (WRITTEN ANSWER REQUIRED)
  Examine the bar box for dividing lines and inset frames.

  ⚠ N=2 MANDATORY GATES — both written answers required before proceeding:

  GATE A — Q1-CHECK:
    Q1-CHECK: Is there a diagonal line from TOP-RIGHT to BOTTOM-LEFT
              with NO horizontal line present?
    Q1: YES → diagonal is a live candidate
    Q1: NO  → diagonal is ruled out; proceed to Q3

  GATE B — LINE-DESC:
    LINE-DESC: [one sentence describing the actual dividing mark(s) you
                see — orientation, position, full-width or partial]

  Both GATE A and GATE B are mandatory for every N=2 bar. Missing either
  is a protocol violation. Only after writing both gates may you work
  through Q1–Q3 below.

  Work through the following questions in order. Stop at the first match.

  Q1: Is N == 2 AND does a single diagonal line run from the TOP-RIGHT corner
      to the BOTTOM-LEFT corner, with no horizontal line present?
      → YES: diagonal split. Go to section A3 below.

  Q2: Does a straight horizontal line span the FULL WIDTH of the bar box,
      cleanly dividing it into a distinct upper half and a distinct lower half?
      → YES: four-square layout. Go to section B below.
      NOTE: If N == 3 you must answer Q2 — the horizontal line is present
      even when it is faint. Look for it actively. Two chords sharing one
      half of the box is proof that the horizontal line exists.
      ⚠ If Q2 = YES and N = 2, do not proceed. Write COUNT CONFLICT and
      recount — a horizontal line with only 2 chords means a vertical
      divider was missed.

  Q3: Is N == 2 AND is there a small square or rectangle framed in the
      BOTTOM-RIGHT corner of the box, distinct from the main area, without
      any horizontal line crossing the full width?
      → YES: bottom-right inset layout. Go to section A2 below.

  ⚠ Q3-CHECK (written answer required for N=2 bars where Q1=NO):
  If Q1 answered NO, you must explicitly check for a bottom-right inset
  frame before declaring the bar undivided.
  Write:
    Q3-CHECK: [Is a small framed square visible in the bottom-right corner?]
    Q3: YES → inset layout
    Q3: NO  → bar is undivided (N=1 expected; write COUNT CONFLICT if N=2)

  Write the answer before proceeding:
  LAYOUT-TYPE: [inset | four-square | diagonal | undivided]

STEP 3 — BOUNDARY BOX RULE FOR THE BAR SUBDIVISION LAYOUT

  When a bar is subdivided (diagonal, inset, or four-square), each chord symbol —
  including any alteration suffixes (b5, #5, b9, #9, m, ø, °, etc.) — must be
  read only from within that beat's own boundary region. Alterations printed
  outside a beat's region, even if visually adjacent, belong exclusively to
  the chord occupying the region where they appear.

  DIAGONAL SPLIT — mandatory suffix-location check:
  Before encoding ANY chord in a diagonal-split bar, perform this
  two-part check for EVERY symbol (alteration or chord-quality suffix)
  you can see in the bar box:

  CHECK A — WHICH TRIANGLE IS IT IN?
  Draw an imaginary line from the TOP-RIGHT corner to the BOTTOM-LEFT
  corner of the bar box. For each symbol, ask: does it sit ABOVE or
  BELOW that line?
    • ABOVE the diagonal → belongs to the upper-left chord (beat 1)
    • BELOW the diagonal → belongs to the lower-right chord (beat 3)
  This is a purely geometric question. Answer it before reading the
  chord symbol. Do not move a suffix across the diagonal for any reason.

  CHECK B — VERTICAL STACKING IN THE LOWER TRIANGLE (WRITTEN ANSWER REQUIRED)
  The root note of the lower-right chord and its alteration suffix are
  often stacked vertically within the lower-right triangle: root on top,
  suffix below (or vice versa). They are BOTH below the diagonal and
  together form ONE chord symbol. Read them as a unit.

  For every diagonal bar, write the following line in the scratchpad
  before encoding any chords:

    LOWER-STACKING: [YES — root <X> and suffix <Y> are both below the
                     diagonal and form one chord: encode <final>]
                 or [NO — no stacked suffix detected in lower triangle]

  This line is mandatory. A diagonal bar with no LOWER-STACKING line
  is a protocol violation.

  ⚠ CRITICAL TRAP — suffix near the upper chord's baseline:
  A suffix that prints just below the diagonal line will appear
  visually adjacent to the upper-left chord. This is the most common
  misread. Proximity to the upper chord is irrelevant. Position
  relative to the diagonal line is the ONLY criterion.
  If the suffix is below the line → it belongs to beat 3. Period.

  ⚠ STACKED SUFFIX IN LOWER TRIANGLE — common misread as upper chord modifier:
  When the lower-right chord symbol is split across two lines within the lower
  triangle (root on one line, alteration suffix on the next line below), the
  suffix will often print close to the baseline of the upper-left chord symbol,
  creating the visual impression that it modifies the upper chord. It does not.
  Both the root and the suffix are below the diagonal and together form the
  single lower-right chord. Perform CHECK B explicitly for every diagonal bar
  before encoding:
    ask "Is this suffix stacked below a root that is itself below the diagonal?"
    If yes → the suffix belongs to beat 3, regardless of how close it sits to
    the upper chord's text.
  Concrete example (do not infer from harmony — read geometry only):
    Bar contains: Am7 (upper-left), diagonal line, B7 (lower-right, top of
    stack), b5 (lower-right, bottom of stack)
    WRONG: upper=Am7_b5, lower=B7  ← b5 was pulled across the diagonal
    CORRECT: upper=Am7, lower=B7_b5  ← b5 is below the diagonal, stacked
    under B7

  Write the LOWER-STACKING answer before encoding:
    UPPER-LEFT (beat 1): [list every symbol above the diagonal]
    LOWER-RIGHT (beat 3): [list every symbol below the diagonal]
  Only then encode the two chords.

  NO HARMONIC INFERENCE — never use chord-type familiarity or harmonic
  context to resolve boundary ambiguity. The fact that a suffix would
  produce a common or expected chord type (e.g. b5 completing a
  half-diminished chord, #5 completing an augmented dominant) is not
  evidence that the suffix belongs to a neighbouring beat's region.
  Assign alterations by region geometry only. Boundary lines are hard
  geometrical limits.

STEP 4 — DECLARE THE RULE (WRITTEN ANSWER REQUIRED)
  Write the rule before encoding any chords:
  LAYOUT: [undivided | inset | diagonal | rule4 | rule5 | rule6]

  ⚠ CONSISTENCY CHECK — before writing this declaration, verify:
    • If N = 2 and a horizontal line is present, STOP — write COUNT
      CONFLICT and recount before proceeding.
    • If N = 3, the declared rule MUST be rule4 or rule5. Never diagonal.
    • If N = 4, the declared rule MUST be rule6.
    • If you find yourself writing LAYOUT: diagonal for a bar where N = 3
      or N = 4, STOP. Go back to Step 1 and recount.

  Only after writing this declaration may you encode the chords.


  A) NO HORIZONTAL DIVIDING LINE → INSET, DIAGONAL, or UNDIVIDED

   A1) UNDIVIDED — one chord, no subdivision lines, no inset frame:
       → chord lasts all 4 beats. Use plain string. Example: "Cm7"

   A2) BOTTOM-RIGHT INSET — no horizontal line, no diagonal line; one chord
       fills the main area of the box; a second chord sits inside a small
       square or rectangle framed exclusively in the bottom-right corner.
       The inset frame is self-contained — it does not extend across the
       full width or height of the box.
       → main area chord   = beats 1–3  → encode on beat "1"
       → inset chord       = beat 4     → encode on beat "4"
       Result: { "beats": { "1": "chordA", "4": "chordB" } }

       NOTE: The main area chord may be any chord type. Do not mistake this
       layout for a diagonal split simply because the main chord occupies a
       large irregular region. The identifying feature is the small framed
       square in the bottom-right corner — if that frame is present, this
       rule applies regardless of how the main area looks.

   A3) DIAGONAL SPLIT — a single diagonal line runs from the TOP-RIGHT corner
       to the BOTTOM-LEFT corner of the box, with NO horizontal line and NO
       bottom-right inset frame present:
       → upper-left triangle  = beats 1+2  → encode on beat "1"
       → lower-right triangle = beats 3+4  → encode on beat "3"
       Result: { "beats": { "1": "chordA", "3": "chordB" } }

   ⚠ DIAGONAL vs. INSET — easy to confuse when scan quality is low:
   A diagonal split has ONE slanted line dividing the box into two triangles
   with no framing in any corner. A bottom-right inset has a small square
   frame in the bottom-right corner only, with the rest of the box forming
   one undivided main area. If a framed corner square is visible, it is an
   inset — not a diagonal.

   ⚠ DIAGONAL vs. RULE 4 — most common confusion with N=3:
   A diagonal split has ONE slanted line and NO horizontal line, and produces
   EXACTLY TWO chords. Rule 4 has a horizontal line across the full box width
   PLUS a vertical line only in the lower half — producing one chord above and
   TWO chords below. If you can see two distinct chords in the lower region of
   the box, the box has a horizontal dividing line and Rule 4 applies,
   regardless of how the lines look at low scan resolution.
   Do not default to diagonal.

   ⚠ DIAGONAL vs. RULE 5 — the most dangerous confusion because it causes a
   chord to be silently dropped from the output entirely:
   A diagonal split has ONE slanted line and NO horizontal line, and produces
   EXACTLY TWO chords. Rule 5 has a horizontal line across the full box width
   PLUS a vertical line only in the upper half — producing THREE chords (two
   side by side above, one below).

   THE ONLY RELIABLE DEFENCE: complete Step 1 honestly before looking at the
   lines. If N = 3, diagonal is already ruled out. The visual impression of a
   diagonal or a large upper-left triangle is a red herring. Two chords sitting
   side-by-side in the upper half of a box is PROOF that a horizontal line is
   present and Rule 5 applies — even when that horizontal line is faint or
   partially obscured by ink at low scan resolution.

   Do not default to diagonal. When in doubt and N = 3, always use Rule 5.

   WHAT RULE 5 LOOKS LIKE AT LOW SCAN RESOLUTION — read this carefully:
   At low resolution the upper-left chord of a Rule 5 bar can look like a
   large triangular region. The vertical divider in the upper half may be
   thin or faint. The lower chord may be printed smaller. All of this can
   create the impression of a diagonal-split bar with a stray chord symbol
   near the top-right. It is not. If you count three distinct chord symbols,
   apply Rule 5. The third chord is NEVER a stray or a repeat symbol — it
   is a real chord occupying beat 2.


  B) HORIZONTAL DIVIDING LINE PRESENT → FOUR-SQUARE SPLIT (Rules 4–6)

   The horizontal line is always present. Additional vertical lines subdivide
   the upper half, the lower half, or both. Choose the rule by counting how
   many chords appear in the upper and lower halves.

   ⚠ If you reach this section with N = 2, stop immediately. Write COUNT
   CONFLICT and recount — a horizontal line combined with exactly 2 chords
   means a vertical divider was missed.

   Rule 4 — ONE chord above, TWO chords below (lower half split vertically):
      → upper chord        = beats 1+2  → encode on beat "1"
      → lower-left chord   = beat 3     → encode on beat "3"
      → lower-right chord  = beat 4     → encode on beat "4"
      Result: { "beats": { "1": "chordA", "3": "chordB", "4": "chordC" } }

      NOTE: Rule 4 is the correct rule whenever one chord occupies the full
      upper half and two distinct chords share the lower half. This is the
      layout most often confused with a diagonal split — the upper chord
      spanning the full width can visually resemble a large triangle. Confirm
      by checking for the horizontal line and the vertical line in the lower
      half before concluding it is a diagonal.

   Rule 5 — TWO chords above (upper half split vertically), ONE chord below:
      → upper-left chord  = beat 1      → encode on beat "1"
      → upper-right chord = beat 2      → encode on beat "2"
      → lower chord       = beats 3+4   → encode on beat "3"
      Result: { "beats": { "1": "chordA", "2": "chordB", "3": "chordC" } }

      NOTE: Rule 5 is the correct rule whenever two distinct chords sit
      side-by-side in the upper region of a box. This is the layout most
      often confused with a diagonal split — at low scan resolution the
      upper-left chord and the dividing lines can resemble a triangle.
      If Step 1 returned N = 3, a diagonal reading is impossible: Rule 5
      (or Rule 4) must apply.

      ⚠ SILENT DROP WARNING: Misclassifying a Rule 5 bar as diagonal causes
      the beat-2 chord to disappear from the output with no error. It is the
      hardest mistake to catch in review precisely because the output looks
      plausible. The only prevention is disciplined Step 1 counting.

   Rule 6 — TWO chords above, TWO chords below (both halves split vertically):
      → upper-left chord   = beat 1  → encode on beat "1"
      → upper-right chord  = beat 2  → encode on beat "2"
      → lower-left chord   = beat 3  → encode on beat "3"
      → lower-right chord  = beat 4  → encode on beat "4"
      Result: { "beats": { "1": "chordA", "2": "chordB", "3": "chordC", "4": "chordD" } }


WORKED EXAMPLE — RULE 5 BAR
-----------------------------
Scenario: a bar box appears to have a large upper-left chord and a smaller
lower region. Three chord symbols are visible: "Eb" upper-left, "G7" upper-right,
"C7" lower.

STEP 1  CHORDS: 3
        → N = 3. Diagonal is IMPOSSIBLE. Must be Rule 4 or Rule 5.

STEP 2  Q2: Is there a horizontal line spanning the full width?
        Yes — the lower chord "C7" is separated from the upper region
        by a horizontal line.
        Two chords share the upper half → Rule 5.
        LAYOUT-TYPE: four-square

STEP 3  No diagonal → no diagonal boundary check needed.

STEP 4  LAYOUT: rule5
        → beat 1 = "Eb"
        → beat 2 = "G7"
        → beat 3 = "C7"
        Encode: { "beats": { "1": "Eb", "2": "G7", "3": "C7" } }

This is NOT encoded as { "beats": { "1": "Eb", "3": "C7" } } with "G7"
reassigned to the next bar. G7 lives in beat 2 of this bar.


WORKED EXAMPLE — DIAGONAL BAR WITH STACKED LOWER SUFFIX
---------------------------------------------------------
Scenario: a bar box has a diagonal line from TOP-RIGHT to BOTTOM-LEFT.
In the upper-left triangle: "Am7". In the lower-right triangle: two lines
of text, "B7" on top and "b5" below.

LOWER-LINE-CHECK (performed before committing to N):
  The lower triangle contains two lines: "B7" (root+interval) and "b5"
  (alteration suffix). Both are below the diagonal. They form ONE chord.
  Chord count for this bar: 2, not 3.

STEP 1  CHORDS: 2 (Am7 above diagonal; B7+b5 below diagonal as one unit)
        → N = 2. Diagonal is a candidate. No COUNT CONFLICT.

STEP 2  Q1-CHECK: Is there a diagonal line from TOP-RIGHT to BOTTOM-LEFT
                  with NO horizontal line present?
        Q1: YES — diagonal line confirmed, no horizontal line.
        LINE-DESC: slanted line running from top-right corner to bottom-left
                   corner; no horizontal line visible anywhere in the box.
        Candidate A: diagonal — ACCEPTED
        LAYOUT: diagonal

STEP 3  CHECK A:
        UPPER-LEFT (beat 1): Am7 — above the diagonal
        LOWER-RIGHT (beat 3): B7, b5 — both below the diagonal

        CHECK B — LOWER-STACKING:
        LOWER-STACKING: YES — "B7" and "b5" are both below the diagonal
        and form one chord. "b5" = flat-5 suffix → encode B7_b5.
        WRONG reading rejected: Am7_b5 (would pull "b5" across the diagonal
        and miscounting the bar as 3 chords, causing a bar-shift cascade).

STEP 4  LAYOUT: diagonal
        → beat 1 = "Am7"
        → beat 3 = "B7_b5"
        Encode: { "beats": { "1": "Am7", "3": "B7_b5" } }


END-OF-ROW SANITY CHECK (mandatory after encoding every row)
-------------------------------------------------------------
After encoding all bars in a row, perform this final check before moving
to the next row:

  ROW-SANITY: I encoded N bars. The form declares M bars per section.
              N == M? [YES / NO — if NO, recount from scratch]

If N ≠ M, do not proceed. Return to the bar boundary pre-pass and recount.
A bar-shift cascade failure will always manifest as the wrong number of bars
encoded in a row. This check is the last line of defence before the error
propagates into the JSON.

Also verify: the total number of chord symbols encoded across the row equals
the total number of chord symbols counted in the chord count pre-pass. If the
totals differ, a chord was silently dropped or duplicated — find it before
proceeding.


REPEAT RULES — ALL CASES
-------------------------
In every case below, ALWAYS write out the actual chord(s) explicitly.
NEVER use "-", "•", "•/•", "→", or any shorthand in the output JSON.

IDENTIFYING THE REPEAT TYPE (mandatory written check):
Before expanding any repeat row or bar, you must identify which repeat
type is present and write it in the scratchpad:

  REPEAT-TYPE: [row-arrow | section-repeat | two-bar-diagonal | bar-repeat | dash]

For rows that begin with a repeat symbol, you must additionally write:

  REPEAT-MARK: [describe exactly what you see — plain arrow, arrow with
                vertical line to its right, or other mark]

This description is mandatory. The distinction between a plain row arrow
(→, repeat rule 2) and a section repeat arrow (arrow + vertical line,
repeat rule 1) is a single thin mark that can disappear at low scan
resolution. If the mark is ambiguous, write:

  REPEAT-MARK: ambiguous — [describe what is and is not visible]

and choose the more conservative interpretation (row arrow, rule 2),
meaning the one that expands fewer bars. Flag any bar-level overrides
as uncertain.

1. FULL SECTION REPEAT (arrow with vertical line between rows):
   Copy all bars from the most recent section with the same letter verbatim.
   If any bar in the repeated row has a chord explicitly written, that chord
   overrides the copied bar for that position.
   REPEAT-TYPE to write: section-repeat

2. ROW ARROW (plain → at the start of a row, no vertical line):
   Copy the entire previous row of the same section verbatim.
   Override any explicitly written bars.
   REPEAT-TYPE to write: row-arrow
   
   ROW-ARROW OVERRIDE IDENTIFICATION (mandatory pre-pass):
   Before expanding a row-arrow repeat, perform a dedicated override-identification 
   pass across the entire row. For every bar box in the row, determine independently 
   whether it contains an explicit chord symbol or a dash/blank.
   Write for every bar:
   ROW-BAR N: [EXPLICIT: <symbol(s) seen>] or [DASH/BLANK: copy from previous row]
   Commit to all 8 override/dash decisions before expanding any bar. Do not identify 
   overrides while simultaneously reading chord content — these are two separate steps. 
   A bar that contains only a dash, a dot, or is visually empty is always a copy. Only 
   bars with a legible chord symbol are overrides.
   This pre-pass prevents a chord symbol inside a multi-chord bar from being misread as 
   occupying an adjacent bar, which shifts all subsequent bars rightward.

3. TWO-BAR DIAGONAL (diagonal line spanning two adjacent bar boxes):
   Copy the immediately preceding two bars verbatim into those two bars.
   Distinct from a single-bar diagonal split (which stays within one box).
   REPEAT-TYPE to write: two-bar-diagonal

4. BAR-LEVEL REPEAT (•/• or similar):
   Copy the immediately preceding bar verbatim.
   REPEAT-TYPE to write: bar-repeat

   ⚠ BAR-LEVEL REPEAT AT SECTION OPENING: If a bar-level repeat mark (•
   or •/•) appears as the very first bar of a section, there is no
   preceding bar within the section. In this case, look back to the last
   bar of the immediately preceding section and copy that bar. If the
   preceding section itself ended with a repeat mark, copy the chord that
   the repeat mark resolved to (i.e. the fully expanded chord), not the
   repeat symbol itself. If no preceding section exists, encode as "-"
   and add a notation_notes entry.

5. DASH (-) in the score:
   Copy the immediately preceding bar verbatim.
   Exception: if "-" appears as the very first bar of a tune with no preceding
   bar at all, encode as "-" (genuine rest).
   REPEAT-TYPE to write: dash

In ALL cases: expand fully in the JSON. Write the chord(s) out. No shortcuts.


SECTION IDs
-----------
- Use the section labels printed on the score (A, B, C, verse, chorus, etc.)
- The first occurrence of a section is labelled with the letter alone: A, B, C.
- Each subsequent occurrence of the same letter appends an incrementing integer
  starting at 1: A1, A2, A3, etc.
  Example: a 32-bar AABA form produces sections A, A1, B, A2.
- Repeated sections (expanded from a section-repeat or row-arrow mark) receive
  their own new section ID in the JSON, just as if they had been written out
  in full on the page.
- Each section is exactly one 8-bar row — one flat array of 8 bar entries.
  Never nest sections. One section ID = one row = 8 bars.


VARIANTS (asterisk annotations)
--------------------------------
When a bar is marked with an asterisk (*) and a footnote provides an alternative:
{
  "section": "<SECTION_ID>",
  "bar": <1-indexed bar number>,
  "context": "melody" | "rhythm" | "general",
  "chords": ["chord1", "chord2"],
  "note": string
}


MISSING CHORD GRID
------------------
When a tune has no chord grid printed:
- Set "sections" to an empty object: {}
- Add to "notation_notes":
  "no_chord_grid": "No chord grid printed. Form indicated as <label>.
                    Chord content must be inferred from standard form."
- Do not invent chord content.
- If the page shows a cross-reference arrow to another tune ("→ IT'S EASY TO REMEMBER"),
  record that in the no_chord_grid note.


FINGERPRINTS
------------
{
  "id": string,          // kebab-case
  "label": string,
  "location": {
    "section": string,
    "bars": [number]     // 1-indexed
  },
  "chords": [string],
  "description": string
}

Look for: ii–V–I, minor ii–V–i, tritone substitutions, Coltrane changes,
chromatic descents/ascents, Lydian dominants (#11), chromatic mediants,
backdoor dominants (bVII7), modal/pedal sections, secondary dominants,
turnarounds, enharmonic pivots, remote bridge modulations, parallel
major/minor shifts, contrafact relationships.


NOTATION NOTES
--------------
{ "symbol_or_key": "explanation" }

Always note when present: enharmonic spellings, ambiguous readings (also append
"?" in the section array), "#5" / "5+" augmented-fifth convention, "t" = "+"
= "#" convention, omitted parenthesised alterations, missing chord grids
(key: "no_chord_grid"), the French "9e de la 14ème" convention (where a chord
labelled with interval 14 means a 7th chord with an added major 7th, i.e. the
interval is counted from the octave rather than the root).


RECORDINGS
----------
{
  "artist": string,
  "year": number,
  "year_uncertain": boolean    // omit if false
}

Year encoding: years appear as 2-digit numbers in the score margin.
- 30–99 → 1930–1999
- 00–29 → 1900-1929. 
- the scanned lead sheets are old and were published before the year 2000.
- When the decade is genuinely ambiguous from context, encode the raw 2-digit
  string as a string in a "year_raw" field instead of "year", and set
  "year_uncertain": true.


SPECIAL CASES
-------------
- Partial title → "title_uncertain": true
- Preserve form labels exactly as printed
- "VARIANTE" / "STATEMENT" footnote → variants entry for asterisk bar above it
- Use page number from score header for "page"
- "Same chord changes as [TUNE X]" or "→ [TUNE X]" at page footer →
  no_chord_grid note with cross-reference; contrafact fingerprint if applicable
